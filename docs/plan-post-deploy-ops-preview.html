Housekeeping

Verificar estado

bash

Si el usuario confirma que quiere borrarlos

bash

Pruebas reales de los flujos que mutan datos

QA en producción

Nunca se probaron en producción, a propósito — para no arriesgar datos reales sin supervisión directa del usuario. Ahora que el stack lleva un tiempo estable, tiene sentido probarlos.

§

Seguir la convención de seguridad ya establecida: toda prueba real contra BAS debe ser Total = 1 peso.

B.1 — Confirmar una factura real

  1. Loguearse en el dashboard.
  2. Cola de revisión → abrir una factura real pendiente.
  3. Confirmar que los datos extraídos son correctos (o corregirlos).
  4. Click "Confirmar factura" (⌘+Enter también sirve).
  5. Verificar: pasa a review_status=confirmed, aparece en Facturas con el estado correcto, dispara el intento automático de BAS (sección "Estado BAS").

B.2 — Reabrir una factura confirmada

  1. Desde una factura confirmada, click "Reabrir factura" en el diálogo de confirmación.
  2. Confirmar que vuelve a needs_review y reaparece en la Cola.
i

Si esa factura ya tenía una Orden de Pago exitosa en BAS, reabrirla no la bloquea — es una decisión de producto documentada, no un bug.

C

Backups de PocketBase

Infra

Hoy el volumen ticket-ai-infra_pocketbase-data no tiene ningún backup, y ya es la fuente de verdad de facturas reales confirmadas.

?

Preguntarle al usuario dónde quiere guardar los backups (S3, Cloudflare R2, Google Drive, otro Droplet) antes de implementar. Ya hay precedente propio: backups a R2 vía rclone en otro proyecto (memoria project_felicity_db_backups) — gotcha conocido: rclone necesita --s3-no-check-bucket con un token R2 no-admin. Probablemente el mismo patrón sirva acá.

Propuesta de implementación

Script /root/v2/backup-pocketbase.sh en el Droplet (ajustar destino según lo que responda el usuario):

bash · backup-pocketbase.sh
#!/bin/bash
set -euo pipefail
TS=$(date -u +%Y%m%d-%H%M%S)
DEST="/root/backups/pocketbase-$TS.tar.gz"
mkdir -p /root/backups
docker run --rm -v ticket-ai-infra_pocketbase-data:/data -v /root/backups:/backup \
  alpine tar czf "/backup/pocketbase-$TS.tar.gz" -C /data .
# subir a destino remoto (ajustar):
# rclone copy "$DEST" remote:bucket/pocketbase-backups/ --s3-no-check-bucket
find /root/backups -name 'pocketbase-*.tar.gz' -mtime +14 -delete

Cron diario:

crontab
0 4 * * * /root/v2/backup-pocketbase.sh >> /var/log/pb-backup.log 2>&1
!

Probar una restauración real al menos una vez — no solo que el backup se genere. Parar pocketbase, restaurar el tar en el volumen, volver a levantar, confirmar que los datos están. Un backup nunca probado no cuenta como backup.

Espacio en disco: ~10GB libres al momento del deploy (revisar de nuevo). Con retención de 14 días y una BD chica no debería ser problema, pero vigilarlo.

D

Monitoreo / alertas

Infra

Nada existe hoy. El Droplet es chico (960MB RAM) — evitar stacks pesados tipo Prometheus+Grafana. De más a menos simple:

1. Uptime check externo — recomendado, gratis, cero carga en el Droplet

UptimeRobot o similar pegándole a https://backend.ticketia.devstage.com.ar/ (y al dashboard, cuando tenga dominio) cada 5 min, con alerta si cae. Requiere que el usuario cree la cuenta — no lo puede hacer Claude sin sus credenciales.

2. Watchdog local simple — cron cada 5 min

bash
#!/bin/bash
cd /root/v2/ticket-ai-infra
DOWN=$(docker compose ps --status exited --format '{{.Service}}')
if [ -n "$DOWN" ]; then
  echo "Servicios caídos: $DOWN" # reemplazar por un curl a un webhook (Slack/Discord/ntfy.sh)
  docker compose up -d
fi

ntfy.sh es la opción más simple para notificaciones push sin cuenta paga si el usuario quiere algo ya mismo sin configurar Slack/Discord.

3. Alertas de recursos

Dado lo ajustado que está el Droplet, un chequeo simple de free/df por cron que avise si RAM disponible <100MB o disco >90% sería barato de agregar — ya se vio swap en uso real durante el deploy.

?

Antes de implementar: preguntarle al usuario qué canal de alertas prefiere (email, Slack, WhatsApp al propio bot, ntfy.sh) — no asumir.

Orden sugerido al retomar

  • 1 Tarea B — probar que todo funciona de verdad en producción; es lo más urgente, valida el deploy end-to-end.
  • 2 Tarea C — backups, antes de seguir usando el sistema en producción sin red de seguridad de datos.
  • 3 Tarea D — monitoreo, para enterarse solo si algo se cae.
  • 4 Tarea A — limpieza, al final, una vez que B/C/D dieron confianza de que el stack nuevo es estable.
